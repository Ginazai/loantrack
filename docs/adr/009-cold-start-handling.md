# ADR-009: Handle sleeping Render services in the client, with an optional keep-alive**Status:** Accepted**Date:** 2026-10-24## ContextThe app runs on Render, where idle services are put to sleep and the next request wakes them. While the backend wakes, the proxy in front of it answered the browser with 502 or 429 (as reported; 503 and 504 are the other usual gateway answers and are handled too). The SPA treated these as ordinary failures, so after any quiet spell the app looked broken until someone opened the backend URL in a browser to wake it manually, and then reloaded.Two things limit what can be fixed server-side. A sleeping backend can't answer anything itself, and the container does real work before serving (`alembic upgrade head`, then the seed script), so a cold start is long.## DecisionMake the client tolerate the wake-up, and make waking it optional to avoid:1. **Warm-up ping on load.** `main.tsx` calls `GET /api/v1/health` immediately, so waking starts while the user is still on the login page.2. **Retry with backoff** in the axios client for cold-start symptoms (502/503/504, a 429 that is not this API's own limiter, network errors): up to 8 retries over about a minute, honouring `Retry-After`, then surface the real error. A banner ("Connecting to the server") explains the wait.3. **Retry only what is safe.** Reads and login/refresh are always resent. Other writes are resent only after 503 or a proxy 429 (known not processed). After 502/504 or a dropped connection they are not resent, because the first attempt may have been recorded, and a duplicate payment is worse than asking the user to retry.4. **The API's own 429 is not retried**, so a real lock-out is shown at once instead of looking like a slow start.5. **Token refresh gets the same retry**, so a 502 during refresh cannot be mistaken for an expired session and log the user out.6. **nginx waits up to 120 s** for the backend (`proxy_connect/send/read_timeout`), instead of giving up at its 60 s default.7. **Optional keep-alive** (`keep-alive.yml`): a scheduled ping of the backend, disabled until the `KEEP_ALIVE_URL` variable is set.## Consequences- After a quiet spell the first request takes about as long as a cold start but succeeds without manual intervention.- A cold start that outlasts the retry window (about a minute plus request time) still ends in an error; reloading retries.- A user who is actually offline sees the "Connecting" banner for about a minute before an error appears, because "no response" can't be told apart from a sleeping backend.- A payment submitted while the backend was asleep and rejected with 502 needs a manual retry.- Backend background loops (webhook retry, cycle-close scan) are in-process ([ADR-006](006-cycle-close-detection-without-worker.md)) and do not run while the service sleeps; the retry logic does not address that, only keeping the service awake does.- The keep-alive workflow trades free-tier instance hours for responsiveness and depends on GitHub's best-effort cron.## Alternatives considered- **Paid always-on instance:** the reliable fix, with a monthly cost. Compatible with this ADR; the client logic then just never triggers.- **Keep-alive only:** cron can be late or disabled, so a cold start would still break the app occasionally.- **Retry everything including all POSTs:** simpler, but risks double-recording payments after a 502/504.- **Longer nginx timeouts alone:** doesn't help when the proxy answers 502/429 immediately instead of holding the request.
